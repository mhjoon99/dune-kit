# PRD 작성법 — `docs/prd/`

전체 흐름은 `process.md`. PRD 는 **무엇을 왜 만드는지**만 적는다. `/prd` 커맨드로 만든다.

## 1. 파일명과 버전

```
docs/prd/
  00-회원-관리_v0.3/                 ← {NN}-{제목}_v{버전}  — 버전마다 폴더 하나
    00-prd_회원-관리_v0.3.md          ← {NN}-prd_{제목}_v{버전}.md
    tech-spec/                       ← 이 버전의 Tech Spec(`tech-spec.md` §2). 없으면 만들지 않는다
      02_결제.md
  00-회원-관리_v0.4/
    00-prd_회원-관리_v0.4.md
```

- **PRD 버전 파일 하나에 폴더 하나다.** 그 버전의 PRD 와 Tech Spec 이 같은 폴더에 있다. 띄어쓰기는 `-`

- `NN` 은 PRD 번호다. 재사용하지 않는다. Card 폴더(`docs/card/{NN}-{제목}_v{앞자리}/`)가 이 번호를 따른다
- 버전은 **파일명과 제목 끝 양쪽**에 적는다

**버전을 가르는 기준은 그 PRD 의 「1. 목적」이다.** PRD 는 "이 기능도 지금 할까요?" 에 답하는 기준선이다(§4).
개발 중에 기능을 더해야 할 때, 그 기능이 목적 안에 있는지로 가른다.

| 더하려는 기능이 | 어떻게 |
|---|---|
| 그 PRD 의 **목적에 맞는다** | 버전은 그대로. 같은 파일의 표에 더하고 **고친 항목 바로 옆에 `(추가_YYYY-MM-DD)`** 를 적는다. 구분이 새로 생겨도 같다 |
| 그 PRD 의 **목적과 어긋난다** | **버전을 올리고(v1.0 → v1.1) 새 파일을 만든다.** 새 파일에는 그 기능의 목적과 **새 기능만** 적는다 |

- **어느 쪽인지는 사용자가 정한다.** 사용자가 기능을 PRD 에 더하자고 하면, 나는 목적의 어느 문장에 맞는지·어긋나는지를
  근거로 어느 쪽인지 **제안만** 한다. 사용자가 정하기 전에는 파일을 고치거나 새로 만들지 않는다
- **새 버전 파일은 누적하지 않는다.** 이전 버전의 기능을 옮겨 적지 않는다. 용어·사용자 절은 달라지는 것만 적는다
- **새 버전은 새 폴더에 만든다.** 이전 버전의 폴더와 파일은 그대로 작업 기준이다. 지우거나 옮기지 않는다. 그 버전의 기능·Card 는 그 파일을 따른다
- 한 PRD 번호의 기능 전체는 **모든 버전 파일을 합친 것**이다. Card·주간보고는 버전 파일을 전부 읽는다
- 앞자리(v1 → v2)를 올리는 기준은 **정하지 않았다.** 올려야 할 것 같으면 사용자에게 묻는다
- 기능·할 일을 고쳤으면 **그 Card 도 같은 작업에서** 고친다(`card.md` §3)

## 2. 템플릿

```markdown
# 🚀 [PRD] 제품 요구사항 정의서: {제목} - v{버전}

> 최종 수정일: YYYY-MM-DD
> 제품/프로젝트 소유자 (PM):
> 상태: ⚪ 초안 (Draft)

- ⚪ 초안 (Draft): 기술 검토 및 작성 중
- 🟡 리뷰 중 (In Review): PM/타 개발자 검토 및 의견 수렴 중
- 🟢 승인됨 (Approved): 구현 방식 확정 및 개발 시작
- ✅ 완료 (Done): 코드 반영, QA 및 릴리즈 완료

## 0. 용어

- {용어}: {뜻}

## 1. 목적

- 해결할 문제:
- 이번에 만들 결과:

## 2. 사용자

- 누가 쓰는가:
- 어떻게 쓰는가:

## 3. 필요한 기능

| 구분 | 기능 | 사용자가 할 수 있어야 하는 일 | 완료 기준 |
|---|---|---|---|
| {구분} | {기능} | • {할 수 있어야 하는 일}<br>• {…} | • {완료 기준}<br>• {…} |
```

## 3. "필요한 기능" 표 — Card 의 출발점

| 열 | Card 에서 |
|---|---|
| 구분 | Card 의 구분 폴더 `{구분 번호}_{구분}`(`card.md` §1) |
| 기능 | **카드 이름.** 기능 하나가 카드 하나다 |
| 사용자가 할 수 있어야 하는 일 | **할 일(Task list).** `•` 하나가 체크박스 하나. 카드에서는 작업자 입장 문장으로 바꾼다(`card.md` §2) |
| 완료 기준 | 완료 조건(Done) |

- 같은 구분이 이어지면 구분 칸을 비워 둔다. 한 칸에 여러 줄은 `•` 와 `<br>` 로 쓴다
- **사용자 관점 문장으로 쓴다.** "무엇을 할 수 있어야 하는가" 이지 "무엇을 구현하는가" 가 아니다
- 주간보고의 ■ 는 이 표의 기능명을, ○ 는 카드의 할 일 문장을 쓴다(`weekly-report.md`). **코드를 모르는 사람이 읽는다**

## 4. 참고 사항 — 왜 쓰는가, 무엇을 담는가

사내 「PRD 작성 매뉴얼」의 참고 사항. 매뉴얼은 "템플릿을 활용해 작성하되 **반드시 준수할 필요는 없다.**
참고 사항을 확인하여 **필요에 따라 편집**한다" 고 한다. PRD 는 세 가지를 위해 쓴다.

- **목표 정렬** — 팀원이 각자 다른 그림을 그리지 않고 하나의 목표를 향하게 한다
- **의사결정의 기준** — 개발 중 "이 기능도 지금 할까요?" 가 나왔을 때 "이번 목표와 맞지 않으니 뺀다" 고 답하는 기준선이다
- **리소스 낭비 방지** — 무엇을 만들지 못 박아, 중간에 기획이 뒤집히거나 엉뚱한 결과물이 나오는 것을 막는다

매뉴얼이 PRD 의 핵심으로 꼽는 다섯 항목이다. **PRD 를 쓰거나 고칠 때 이 표로 빠진 것이 없는지 확인한다.**
앞의 셋은 템플릿에 절이 있고, 뒤의 둘은 템플릿에 없다 — 필요에 따라 절을 더한다(더할지는 사용자와 정한다).

| 항목 | 절 | 무엇을 쓰나 | 왜 |
|---|---|---|---|
| 배경과 문제 정의 (Why) | 1. 목적 | 사용자가 어떤 불편을 겪는지, **왜 지금** 만들어야 하는지 | 납득이 돼야 읽는 사람이 '작업자' 가 아니라 '문제 해결자' 로서 더 나은 안을 낸다 |
| 타겟 유저 (Who) | 2. 사용자 | 실제로 쓸 사람을 **구체적으로 좁혀** 쓴다 | "모두를 위한 기능" 은 "아무도 쓰지 않는 기능" 이 되기 쉽다 |
| 요구사항 명세 (What) | 3. 필요한 기능 | 사용자가 할 수 있어야 하는 행동(유저 스토리)과 그에 필요한 기능. 예: "카카오톡 계정으로 3초 만에 로그인할 수 있어야 한다" | Tech Spec 과 디자인이 시작되는 뼈대다 |
| 이번 범위에서 제외할 것 (Out of Scope) | (더한다) | 논의됐지만 이번 릴리즈에서 만들지 않기로 한 것 | 일정이 한없이 늘어나는 것(Scope Creep)을 막는 방어막이다 |
| 성공 지표 (Success Metrics) | (더한다) | 배포 뒤 '성공했다' 고 판단할 **데이터 기준**. 예: "전환율 15% 상승", "CS 문의 30% 감소" | 수치가 있어야 배포 뒤 회고와 개선이 된다 |

## 5. 짧게 쓴다

- **템플릿은 네 절(용어·목적·사용자·필요한 기능)이다.** 제외할 것·성공 지표는 §4 대로 필요에 따라 더한다. 길어지면 PRD 가 아니다
- API 경로·필드 이름·계약값·파일 경로·타임라인·위험 분석을 PRD 에 쓰지 않는다. 그건 **Tech Spec** 이다
- **문서체로 쓴다**. "~의 몫이다", "우리는 ~까지 한다", "누구나 쓴다" 같은 구어·대화체를 쓰지 않는다.
  주어는 "우리" 가 아니라 **"이 PRD"·시스템 이름**으로, 범위는 **어느 문서에 작성하는지**로 적는다
  구어 동사는 문서 용어로 바꾼다 — 쓴다 → 사용한다, 묻는다 → 조회한다, 뺐다 → 제외한다, 들어온다 → 진입한다,
  기댄다 → 의존한다, 빠진다 → 누락된다, 따로 → 별도로. **머리말·용어·목적·사용자·제외할 것·성공 지표 전부에 적용한다**
  - ✗ `통계 화면 — 통계 담당의 몫이다. 우리는 이용 기록을 남기는 데까지 한다`
  - ○ `통계 화면 — 통계 PRD 에 작성. 이 PRD 는 이용 기록을 남기는 데까지만 작성한다`
- 템플릿을 반드시 그대로 지킬 필요는 없다. 절을 더하거나 빼려면 사용자에게 묻는다(`process.md` §2)

## 6. 완료

- **버전 파일마다 따로 완료한다.** 그 버전 파일의 기능에서 나온 Card 가 전부 완료되면 그 파일 머리의 상태를 `✅ 완료` 로 바꾼다
- **`docs/prd/` 안의 문서는 완료돼도 `docs/trash/` 로 옮기지 않는다**(`process.md` §5)
