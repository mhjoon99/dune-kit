# Tech Spec 작성법 — `docs/prd/{PRD 버전 폴더}/tech-spec/`

전체 흐름은 `process.md`. Tech Spec 은 PRD 의 요구사항을 **어떻게 구현할지** 적는다. `/tech-spec` 커맨드로 만든다.

## 1. 선택 문서다

시스템을 구체적으로 설명해야 하거나 구현 아이디어를 구체화할 필요가 있을 때만 쓴다.
PRD 기능이 작아 Card 만으로 충분하면 쓰지 않는다. 쓸지 애매하면 사용자에게 묻는다.

## 2. 파일명

```
docs/prd/
  00-회원-관리_v0.3/                 ← PRD 버전 폴더(`prd.md` §1)
    00-prd_회원-관리_v0.3.md
    tech-spec/
      01_로그인.md                    ← {구분 번호}_{구분}.md
      02_결제.md
  00-회원-관리_v0.4/
    00-prd_회원-관리_v0.4.md
    tech-spec/
      02_결제.md                      ← v0.4 가 기존 구분에 더한 기능
      03_알림.md                      ← v0.4 에서 새로 생긴 구분
```

- **Tech Spec 은 그 기능이 적힌 PRD 버전의 폴더에 둔다.** 어느 PRD 의 어느 버전 것인지는 폴더가 가진다
- **파일명은 Card 의 구분 폴더와 같은 번호·이름이다**(`docs/card/00-회원-관리_v0/02_결제/` ↔ `02_결제.md`). 띄어쓰기는 `-`
- **구분 번호는 `card.md` §1 의 규칙 그대로다** — 그 PRD 번호의 모든 버전 파일의 "필요한 기능" 표를 낮은 버전부터 보아
  구분이 처음 나온 순서. Card 구분 폴더가 이미 있으면(`docs/trash/complete/card/` 포함) 그 번호를 쓴다.
  Tech Spec 을 Card 보다 먼저 써도 같은 규칙으로 번호를 내므로, 나중에 만드는 구분 폴더와 번호가 같아진다
- **새 버전이 이미 있는 구분에 기능을 더하면 새 버전 폴더에 같은 파일명으로 새로 쓴다.** 새 버전의 기능만 다루고,
  이전 버전의 Tech Spec 은 고치지 않는다. 같은 버전 안에서 `(추가_YYYY-MM-DD)` 로 더한 기능은 그 버전의 Tech Spec 을 고친다
- Tech Spec 은 선택 문서라 번호가 비는 구분이 있다. 그 구분은 Tech Spec 이 없다는 뜻이다. 번호를 당겨 쓰지 않는다
- 번호는 바꾸지 않는다. 폐기해도 그 번호를 다른 구분에 주지 않는다 — 지난 문서의 인용이 엉뚱한 데를 가리키면 안 된다
- 인용은 PRD 번호·버전·구분 번호와 절로 한다(`00 v0.4 02 §3`). 같은 버전 폴더 안에서는 구분 번호와 절만 써도 된다(`02 §3`)

## 3. 템플릿

````markdown
# 🛠️ [Tech Spec] 기술 명세서: [기능/모듈명 입력]

> **상위 PRD 링크:** [Docmost의 관련 PRD 문서 URL 첨부]  
> **최종 수정일:** YYYY-MM-DD  
> **테크 리드 / 작성자:** @개발자A  
> **담당 팀원:** @개발자A, @디자이너B  
> **상태:** 
- ⚪ 초안 (Draft): 기술 검토 및 작성 중
- 🟡 리뷰 중 (In Review): PM/타 개발자 검토 및 의견 수렴 중
- 🟢 승인됨 (Approved): 구현 방식 확정 및 개발 시작
- ✅ 완료 (Done): 코드 반영, QA 및 릴리즈 완료


## 1. 개요 및 구현 목표 (Overview)
* **목적:** (상위 PRD의 요구사항을 구현하기 위해 이 문서에서 다루는 기술적 범위 1~2줄 요약)
  * 예: *유저의 매일 방문을 유도하기 위한 출석체크 API 및 DB 로직 구현*
* **핵심 유저/데이터 플로우:**  
  `유저 접속/클릭` ➔ `[Front] API 요청` ➔ `[Back] 중복/연속 출석 검증` ➔ `[DB] 포인트 및 이력 저장`

## 2. 작업 범위 (Scope Boundary)
* **In-Scope (기술적 구현 범위):**
  - [ ] 매일 1회 출석체크 처리 및 포인트 적립 API
  - [ ] 연속 7일 출석 시 추가 1,000p 지급 로직
* **Out-of-Scope (이번에 구현하지 않는 것):**
  - ❌ (예: 소셜 미디어로 출석 인증샷 공유 API)
  - ❌ (예: 놓친 출석일 복구 아이템 관련 DB 설계)

## 3. 기술 상세 설계 (Technical Design)
### ① DB 스키마 / 데이터 모델 (Data Model)
* `attendance_logs`: `user_id`, `checked_at`, `consecutive_days`

### ② API 명세 (API Design)
* **`POST /api/v1/attendance`**
  * **Req:** `{ "userId": "123" }`
  * **Res:** `{ "status": "SUCCESS", "earnedPoint": 100, "consecutiveDays": 3 }`

## 4. 완료 기준 (Definition of Done, DoD)
> *이 기준이 모두 만족되어야 Planka의 카드를 'Done'으로 이동할 수 있습니다.*

- [ ] **[백엔드]** 포인트 지급 및 연속 출석 체크 API 개발 & 테스트 코드 통과
- [ ] **[프론트]** 출석체크 위젯 UI 개발 및 API 연동 완료
- [ ] **[QA/디자인]** 디자인 검수(QA) 통과 및 승인
- [ ] **[문서화]** API 변경사항 Docmost 최종 반영 완료
````

Tech Spec 작성 시 위 템플릿을 활용하여 작성한다. 본 문서는 Optional 한 문서로, 시스템에 대한 구체적 description 이
필요하거나 담당자가 아이디어 등을 구체화할 필요가 있는 경우 작성하는 것을 원칙으로 한다. 다만 PRD 와 마찬가지로
반드시 준수할 필요는 없다. 아래 참고 사항을 확인하여 필요에 따라 편집한다.

## 4. 참고 사항 (사내 「업무프로세스 V1.0」 원문)

### Tech Spec 을 작성하는 핵심 목적

- **위험 최소화 (Risk Mitigation):** 개발을 절반쯤 진행했는데 "어, 이거 기존 DB 구조로는 불가능한데요?" 라며 코드를 다 뜯어고치는 대참사를 사전에 방지한다.
- **병렬 작업의 기준 (Parallel Work):** 프론트엔드와 백엔드가 서로를 기다릴 필요 없이, 명세서에 약속된 규격(API)을 바탕으로 동시에 개발을 시작할 수 있게 해 준다.
- **지식의 자산화 (Knowledge Transfer):** 이 코드를 짠 담당자가 퇴사하거나 휴가를 가더라도, 다른 엔지니어가 문서를 보고 전체 구조를 파악하고 유지보수할 수 있도록 돕는다.

### Tech Spec 에 반드시 작성해야 하는 5가지 핵심 항목

1. **시스템 아키텍처 (System Architecture)**
   - 내용: 신규 기능이 기존 시스템(서버, 클라이언트, 외부 연동 등)에 어떻게 연결되는지 큰 그림(구조도)을 그린다. 구조도를 그릴 때는 mermaid 문으로 작성한다.
   - 이유: 이 기능이 전체 시스템 성능에 미치는 영향도를 파악하고, 기술적 타당성을 검증하기 위함이다.
2. **데이터베이스 스키마 및 데이터 모델 (DB Schema)**
   - 내용: 어떤 테이블을 새로 만들고 기존 테이블에 어떤 컬럼을 추가할지, 데이터 간의 관계(ERD)는 어떻게 짤 것인지 정의한다.
   - 이유: 데이터 구조는 한 번 잘못 설계하여 라이브 서버에 반영되면 나중에 수정하기가 가장 고통스럽고 위험한 영역이기 때문이다.
3. **API 명세 (API Specifications)**
   - 내용: 엔드포인트(URL), HTTP 메서드(GET, POST 등), Request/Response 데이터 포맷(JSON 구조)을 구체적으로 약속한다.
   - 이유: 프론트엔드와 백엔드 개발자 간의 '계약서' 역할을 하여, "API 언제 나와요?", "왜 데이터가 이렇게 오죠?" 같은 커뮤니케이션 비용을 없애 준다.
4. **예외 처리 및 엣지 케이스 (Edge Cases & Error Handling)**
   - 내용: 트래픽이 갑자기 몰렸을 때, 유저가 비정상적인 값을 입력했을 때, 외부 API(예: 결제사 서버)가 응답하지 않을 때 어떻게 방어할지 적는다.
   - 이유: 정상적으로 작동하는 해피 패스(Happy Path)만 생각하고 코드를 짜면 필연적으로 치명적인 버그와 서비스 장애가 발생하기 때문이다.
5. **보안 및 성능 고려사항 (Security & Performance)**
   - 내용: 민감한 개인정보는 어떻게 암호화/마스킹할지, 특정 API 호출이 잦아 병목이 예상될 때 캐싱(Caching)을 어떻게 적용할지 명시한다.
   - 이유: 보안 사고나 서버 다운 같은 치명적인 비즈니스 리스크를 설계 단계에서 미리 차단하기 위해서이다.

## 5. 쓸 때 지키는 것

- **`## 3. 기술 상세 설계` 에 위 5가지 핵심 항목을 모두 쓴다.** 템플릿에는 DB 스키마·API 명세 둘만 있으므로
  나머지 셋을 더해 **① 시스템 아키텍처 ② DB 스키마 ③ API 명세 ④ 예외 처리·엣지 케이스 ⑤ 보안·성능** 순서로 둔다.
  해당이 없으면 절을 지우지 않고 `해당 없음 — {이유}` 한 줄을 적는다 — 빠뜨린 것인지 없는 것인지 구분돼야 한다
  - ① 은 구조도(**mermaid** — §4 의 1번)와 **구성 요소 ↔ 코드 경로** 표, 그리고 기존 시스템과 **부딪히는 곳**을 적는다
  - ② 는 테이블·컬럼과 함께 **관계**(무엇이 무엇을 가리키나, 같은 트랜잭션에 쓰이는 것)와 migration 번호를 적는다
  - ③ 은 경로만 늘어놓지 않고 **Req·Res 를 JSON 으로** 적는다. 프론트가 이 절만 보고 타입을 만들 수 있어야 한다
  - ④ 는 참고 사항의 세 갈래(트래픽 급증 / 비정상 입력 / 외부 무응답)를 빠짐없이 훑는다
  - ⑤ 는 무엇을 저장하지 않는지, 무엇을 마스킹하는지, 병목이 어디고 캐시를 어디에 두는지(또는 일부러 안 두는지)
- **다 쓴 뒤 핵심 목적 3가지로 한 번 읽는다** — 기존 구조와 부딪히는 곳이 적혔나(위험 최소화), 프론트가 ③ 만 보고
  시작할 수 있나(병렬 작업), 코드를 모르는 사람이 ① 로 구조를 잡을 수 있나(지식의 자산화)
- **PRD "필요한 기능" 표의 구분 하나에 Tech Spec 하나를 쓴다**. PRD 버전 폴더마다 따로 쓴다(§2).
  이미 있는 Tech Spec 은 PRD 버전이 올라가도 옮기거나 다시 쓰지 않는다
- **근거는 정본(합의된 명세 문서)의 절 번호로 적는다**(`{정본 파일} §2-1`). "명세서 참고" 로 끝내지 말고
  계약값을 옮겨 적는다 — 정본이 바뀌면 어느 문장을 고쳐야 하는지가 번호로 드러난다
- **문서에 없는 값을 그럴듯하게 채우지 않는다.** 실측 뒤 채울 값은 빈칸으로 둔다(`p95 ____초`)
- **결정이 남아 있으면 §2 끝에 `### 팀 결정 대기` 를 둔다.** 이 절이 비어야 상태를 `🟢 승인됨` 으로 올린다.
  결정이 나에게 없으면 `docs/detected_issues.md` 로(`core.md` §4)
- **카드 표를 두지 않는다.** Card 는 PRD 의 "필요한 기능" 표에서 나온다(`card.md`). 구현 순서는 착수할 때 정한다
- Out-of-Scope 는 어디 소속인지 적는다("→ Tech Spec 03", "→ 다른 팀(통계)")

## 6. 완료

- §2 In-Scope 와 §4 DoD 의 체크는 **테스트 검증을 통과한 뒤에만** `[x]` 로 바꾸고 옆에 완료 시각을 적는다
  (`- [x] … 완료:2026-08-14 오후 5:24`, 표기는 `docs-format.md`). 취소선은 쓰지 않고 항목을 지우지 않는다
- 전부 `[x]` 면 문서 머리의 상태를 `✅ 완료` 로 바꾼다
- **완료돼도 `docs/trash/` 로 옮기지 않는다**(`process.md` §5)
