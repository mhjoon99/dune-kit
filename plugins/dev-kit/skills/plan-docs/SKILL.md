# 플랜 작성·운영법 — `docs/plans/`

플랜은 **착수 전에 어떻게 할지 짜서 사용자에게 확인받는 문서**다. 언제 쓰는지는 dev-kit 플랜 규칙(새 기능이거나 고칠 파일 3개 이상)을 따른다.

`docs/plans/` **바로 아래의 낱개 파일**은 플랜이 아니라 사용자가 읽을 문서(다음 할 일·인계·정리)다. 이 형식을 적용하지 않는다.

## 1. 짜는 순서

1. **탐색** — 읽기만 한다. `graphify-out/` 이 있으면 먼저 읽는다(`GRAPH_REPORT.md`, `graphify query`). 없으면 `/codemap` 으로 만들지 사용자에게 제안하고, 거절하면 직접 탐색한다.
   `planner`·`code-explorer` 에이전트는 여기서 **분석용으로만** 쓴다 — 서브에이전트는 사용자에게 질문할 수 없고, 그 출력은 플랜이 아니라 초안의 재료다.
   요청이 모호해 무엇을 탐색할지도 모르면 범위 질문 한두 개를 탐색보다 먼저 한다.
2. **딥인터뷰** — 탐색으로 정할 수 없는 것을 사용자에게 묻는다: 범위, 방식, 계약값, 건드리면 안 되는 곳, 우선순위. 답에서 새 질문이 나오면 이어서 묻는다.
3. **초안** — 아래 형식으로 쓴다. 문서·코드·인터뷰에 없는 값은 지어내지 않는다. 빈칸으로 두거나 「0. 먼저 결정할 것」에 올린다.
4. **컨펌** — 사용자가 읽고 확인한다. 컨펌 뒤에는 범위를 넓히지 않는다. 넓혀야 하면 다시 묻는다.
5. **착수** — 컨펌은 착수 지시가 아니다. 따로 지시받은 뒤 시작한다.

## 2. 폴더와 파일명

Card(`docs/card/`)를 쓰는 프로젝트면 Card 경로를 그대로 따르고, 없으면 작업 이름으로 폴더를 만든다.

```
# Card 가 있을 때 — 카드 경로를 그대로
docs/card/{PRD 폴더}/{구분 폴더}/{순서}_{기능명}.md
docs/plans/{PRD 폴더}/{구분 폴더}/{순서}_{기능명}/

# Card 가 없을 때 — 작업 기준
docs/plans/{작업명}/

  00_차수.md           차수 계획표 (§3)
  1a_서명-모듈.md       1차 a. 같은 숫자끼리는 동시에 진행해도 된다
  1b_오류-계약.md       1차 b
  2a_진입-라우터.md     2차. 1차 검증이 끝나야 시작한다
  9_통합.md            공유 파일과 전체 검증 (§5)
```

- 파일명은 `{차수}{담당}_{제목}.md`. **숫자가 순서, 문자가 동시에 진행하는 자리**다. 한 차수에 최대 3개(a·b·c)
- **플랜 파일 하나는 서로 겹치지 않는 소스·테스트 파일 묶음 하나다.** 할 일 하나에 파일 하나가 아니다 —
  할 일은 기능 단위 문장이라 하나가 API·화면·마이그레이션에 걸치고, 그대로 쪼개면 같은 파일을 둘이 고친다
- 인용은 `1a`, `2a §3` 처럼 한다
- 플랜이 하나뿐이면 `00_차수.md` 와 `9_통합.md` 없이 `1a_….md` 하나만 둬도 된다

## 3. `00_차수.md` — 차수 계획표

```markdown
# 차수 계획: {카드 제목 또는 작업명}

> 기준: `docs/card/{…}.md` 또는 요청 요약 한 줄 / 작성일 / 상태: 컨펌 대기 | 컨펌됨:YYYY-MM-DD | 실행중 | 완료

## 할 일 ↔ 플랜
| Card 의 할 일 (Card 가 없으면: 요청받은 일) | 채우는 플랜 |
한 할 일을 여러 플랜이 채울 수 있다. 그 플랜이 전부 끝나야 그 할 일이 끝난 것이다.

## 진행
| 차수 | 플랜 | 상태 | 산출 |
상태는 대기 / 준비됨 / 구현중 / 검증중 / 완료 / 중단.

## 차수 {n}
| 플랜 | 파일 (소스·테스트 전부) | 앞 차수에서 받는 것 |

## 공유 파일
| 경로 | 이 작업에서 무엇이 바뀌나 | 어느 차수에 반영 |

## 소유권 밖
아무도 건드리지 않는 경로.
```

차수를 나누는 규칙 넷.

1. **의존이 있으면 다른 차수.** A 가 B 의 심볼을 import 하면 B 가 앞 차수다
2. **한 파일은 한 플랜.** 같은 차수의 두 플랜에 같은 경로를 주지 않는다. 테스트 파일도 파일이다
3. **공유 파일은 어느 플랜도 안 받는다.** `9_통합.md` 가 맡는다(§5). 플랜에는 `공유 파일 요청` 으로만 적는다
4. **한 차수에 플랜 최대 3개.** 넘치면 차수를 쪼갠다

## 4. 플랜 파일 골격

```markdown
# {제목}

> 기준: `docs/card/{…}.md` 또는 작업명 / 차수·담당: 2차 a / 선행: 1a, 1b / 상태: 컨펌 대기

## 0. 먼저 결정할 것        ← 최상단 필수. 비어 있어야 실행할 수 있다
## 1. 대상                 ← 채우는 할 일, 근거(문서의 절 번호·Tech Spec 절·인터뷰 답)
## 2. 파일
| 경로 | 신규/수정 | 내용 | 근거 |
내 몫(소스·테스트) / 건드리지 않는 것(같은 차수 다른 플랜의 파일) / 공유 파일 요청(경로와 내용)
## 3. 계약값·테스트 케이스
| 항목 | 값 | 근거 |
| 테스트 파일 | 케이스 |
## 4. 체크리스트           ← 최하단
```

- **`## 0. 먼저 결정할 것` 이 비어야 실행한다.** 남아 있으면 사용자에게 묻는 것부터 한다
- **근거는 문서의 절 번호로 적고 계약값을 옮겨 적는다.** 문서에 없는 값을 그럴듯하게 채우지 않는다.
  실측 뒤 채울 값은 빈칸으로 둔다(`p95 ____초`)
- 신규/수정은 **이 저장소의 실태로** 판정한다. 다른 문서가 수정이라고 적었어도 여기 그 파일이 없으면 신규다
- 플랜이 곧 구현자가 읽는 명세다

## 5. `9_통합.md` — 공유 파일과 전체 검증

여럿이 건드리는 파일은 플랜들이 나눠 갖지 않고 통합 플랜이 혼자 맡는다. 무엇이 공유 파일인지는 프로젝트마다 다르므로 탐색 단계에서 찾아 아래 표를 채운다.

| 경로 | 왜 |
|---|---|
| (예: 설정 모듈) | 거의 모든 플랜이 설정을 더한다 |
| (예: 앱 진입점·라우터 등록) | 등록이 한 자리에 모인다 |
| (예: 마이그레이션 폴더) | 번호가 충돌하면 되돌리기 어렵다 |
| (예: 의존성 파일 `pyproject.toml`) | 의존성 추가는 승인 대상이다 |

공유 파일을 건드리지 않는 작업이면 `9_통합.md` 에는 전체 검증과 코드 리뷰만 남는다.

## 6. 완료 표시 — 체크박스 + 완료 시각

체크박스를 `[x]` 로 바꾸고 **옆에 완료 시각을 적는다.**

```markdown
- [x] 구현 + 테스트 완료:2026-08-14 오후 5:24
```

- **취소선은 쓰지 않는다. 항목을 지우지 않는다.** 완료 표시로 이력을 남긴다
- 일부만 끝났으면 끝난 체크 항목만 `[x]` 로

## 7. 완료 표시 전 테스트 검증

**테스트 통과를 확인한 뒤에만** `[x]` 로 바꾼다. 검증 없는 완료 표시를 금지한다.

| 시점 | 범위 |
|---|---|
| 플랜 파일을 끝낼 때마다 | 그 플랜의 테스트 + 린트 |
| **커밋 직전 1회** | **전체 스위트** |
| 모든 플랜이 끝난 뒤 | 통합 검증, 그다음 **코드 리뷰 한 번**(합쳐진 상태를 본다. `/mr-review`) |

검증 명령은 프로젝트의 것을 쓴다(CLAUDE.md, `pyproject.toml`, `package.json` 에서 확인). 찾지 못하면 사용자에게 묻는다.

테스트가 실패하면 **완료가 아니다.** 실패 출력을 그대로 보고한다.
§4 의 3 에 적은 케이스가 실제 테스트 파일에 있는지도 함께 본다 — 문서에만 있는 케이스는 검증이 아니다.

## 8. 종료 판정과 이동

**체크리스트 전 항목이 `[x]` 이고 검증까지 끝나면** 그 플랜은 완료다.

- **모든 플랜이 끝나면** 플랜 폴더를 구조째 옮긴다. 일부만 끝났으면 옮기지 않는다

  ```
  docs/plans/{폴더}/  →  docs/trash/complete/plans/{폴더}/
  ```

- Card 가 있으면 옮기면서 **Card 의 해당 할 일을 `[x]` 로** 바꾼다(`00_차수.md` 의 대응표)
